1. VISÃO GERAL
────────────────────────────────────────────────────────────────────────────────

Sistema de tokenização imobiliária. Cada imóvel cadastrado recebe uma oferta
de tokens: 1 token = R$ 1,00. Tenants (inquilinos) compram frações do imóvel
via PIX ou boleto. Co-owners recebem distribuição de aluguel proporcional à
sua participação no token.

Regra de negócio central:
  - Imóvel de R$ 160.000 → total_supply = 160.000 tokens
  - Dois mercados:
      Primário:   co-owner compra da plataforma (1 → 1, transfer_property_tokens)
      Secundário: tenant compra dos co-owners   (N → 1, settle_token_redistribution)
  - KYC obrigatório (status = 'verified') antes de qualquer transação de token
  - Arredondamento monetário sempre floor (para baixo) — floorMoney / floorOwnershipPercent
  - Taxas pagas pelos dois lados: taxa_plataforma + taxa_token por transação
  - CPF / documento nunca armazenado em texto puro:
      cifrado AES-256-GCM (DOCUMENT_ENCRYPTION_KEY via Infisical) + hash SHA-256 + last4
  - LEDGER_MODE=db → blockchain desabilitado (kill switch por env var, nunca por remoção de código)

4. CAMADA DE WORKERS E JOBS
────────────────────────────────────────────────────────────────────────────────

4A. BULLMQ WORKERS (processo separado, mesmo Railway ou sidecar)

  Email Worker — propya.email.delivery
    Consumer da fila. Chama Resend API.
    Configuração: 3 tentativas / backoff 5 s
    Tipos de e-mail: passwordReset, emailVerification, welcome, tokenPurchase,
                     tokenPurchaseReceipt, rentDistribution, refundOpened,
                     refundCompleted, tokenSaleNotice

  Payment Reconciler — propya.payments.reconcile
    Consumer da fila. Concilia status de pagamentos com Asaas.
    Configuração: 8 tentativas / concurrency = 5
    Acionado: webhook Asaas confirma pagamento → push na fila → worker processa
    Resultado: atualiza payment_transactions + ledger off-chain + status da ordem

  Token Settlement Worker — propya.tokens.settlement  [DESABILITADO]
    Worker NUNCA inicializa quando LEDGER_MODE=db.
    isOffChainLedger() = true → código de inicialização do worker é pulado.
    Jobs publicados na fila ficam em espera indefinidamente (sem consumidor).

4B. CRON JOBS (GitHub Actions → scripts Node.js standalone, saída exit 0/1)

  generate-rent-charges              → mensal
    Gera cobranças de aluguel para todos os contratos ativos.

  finalize-token-settlements         → recorrente
    LEDGER_MODE=db → chama reconcileOffChainSettlements() (sem blockchain).
    LEDGER_MODE=chain → executa blockchain saga (desabilitado em produção).

  generate-boleto-notifications      → diário 03h UTC
    Notifica tenants sobre boletos próximos do vencimento.

  deliver-scheduled-notifications    → diário 09h UTC
    Entrega notificações agendadas (in-app + e-mail).

  pay-owner-payouts                  → periódico
    Calcula accruals de co-owners e dispara PIX via Asaas.

  reconcile-rent-charge-validations  → crash recovery
    Reconcilia cobranças que ficaram em estado intermediário (crash recovery).

  refund-failed-orders               → periódico
    Reembolsa ordens de token que falharam após confirmação de pagamento.

5. PERSISTÊNCIA — SUPABASE (PostgreSQL + Storage)
────────────────────────────────────────────────────────────────────────────────

Client      : @supabase/supabase-js (service role key — nunca exposto ao frontend)
Acesso      : PostgREST (REST sobre PostgreSQL)
Storage     : bucket de documentos KYC (imagens de identidade)

SCHEMA: admin_panel
  users                     → cadastro de usuários (senha bcrypt, sem CPF plaintext)
  roles                     → papéis (admin, tenant, co-owner, …)
  permissions               → permissões granulares (admin.kyc.approve, …)
  pages                     → páginas registradas no sistema de acesso
  user_roles                → M:N usuário ↔ papel
  role_permissions          → M:N papel ↔ permissão
  permission_pages          → M:N permissão ↔ página
  notifications             → notificações in-app
  email_delivery_logs       → log de cada e-mail enviado (Resend message_id)
  notification_job_runs     → controle de execução dos jobs de notificação

SCHEMA: property_mgmt
  properties                → imóveis cadastrados
  property_users            → M:N imóvel ↔ usuário (co-owner / tenant)
  rental_contracts          → contratos de aluguel
  rent_charges              → cobranças mensais de aluguel
  rent_adjustments          → ajustes contratuais de aluguel
  parameter_sets            → parâmetros por imóvel (taxa_plataforma, min_payout…)
  kyc_requirements          → requisitos de KYC por imóvel
  user_kyc_profiles         → perfil KYC do tenant (status: pending/verified/rejected)
  kyc_document_reviews      → revisão admin de documentos
  didit_kyc_sessions        → sessões criadas no Didit (session_id, URL, status)
  user_identity_profiles    → dados biométricos extraídos pelo Didit (nome, nascimento…)
  user_platform_bans        → banimentos de plataforma (resultado do banClassifier Didit)

SCHEMA: token_system
  wallets                       → carteira por usuário (balance em tokens)
  property_tokenizations        → oferta de tokens por imóvel (total_supply, price…)
  token_orders                  → ordens de compra de token
  payment_transactions          → transações de pagamento (Asaas payment_id, status…)
  token_transactions            → movimentações de token (mint, transfer, burn…)
  wallet_token_balances         → saldo por carteira + token (snapshot)
  user_property_token_balances  → saldo por usuário + imóvel (usado no extrato PDF)
  transfer_whitelist            → whitelist de endereços blockchain (desabilitado)
  blockchain_events             → eventos on-chain registrados (desabilitado)

SCHEMA: tokenomics
  distribution_runs                → execuções do job de distribuição de aluguel
  owner_distribution_snapshots     → snapshot da participação de cada co-owner
  distribution_ledger              → ledger de distribuição (idempotency_key UNIQUE)
  owner_payout_accruals            → acumulado de payout por co-owner
  owner_payout_accrual_entries     → entradas individuais de accrual

PADRÕES TRANSVERSAIS:
  - SCD2: tabelas *_history registram versões anteriores de registros mutáveis
  - audit_logs: presente em todos os schemas (quem alterou, quando, o quê)
  - Idempotência via idempotency_key UNIQUE nas tabelas de ledger
  - 1 token = R$ 1,00 (invariante de negócio, não configurável)

MIGRATIONS (convenção de nome: YYYYMMDDNNNN_descricao.sql):
  Aplicadas sequencialmente via psql com DATABASE_URL.
  13 migrations escritas aguardando aplicação no banco de staging/produção.

ASAAS — PSP (Payment Service Provider)
  Ambiente  : sandbox.asaas.com/api/v3 (produção: www.asaas.com/api/v3)
  Auth      : header "access_token: <ASAAS_API_KEY>"
  Endpoints usados:
    POST /customers                       → cadastra cliente (CPF ou foreignCustomer)
    POST /payments                        → cria cobrança PIX ou boleto
    GET  /payments/:id                    → consulta status
    GET  /payments/:id/pixQrCode          → QR Code + copia-e-cola
    GET  /payments/:id/identificationField → linha digitável do boleto
    POST /payments/:id/refund             → estorna pagamento
    POST /transfers                       → PIX para co-owners (pay-owner-payouts)
  Webhook:
    POST /webhooks/asaas/payments (publicRoute)
    Payloads tratados: PAYMENT_CONFIRMED, PAYMENT_OVERDUE, PAYMENT_REFUNDED, …
    req.rawBody disponível para validação HMAC
    Confirmado → push na propya.payments.reconcile → Payment Reconciler

DIDIT — KYC Automatizado
  Ambiente  : verification.didit.me
  Auth      : Bearer DIDIT_API_KEY
  Endpoints usados:
    POST /v3/session/    → cria sessão KYC, retorna URL enviada ao browser do tenant
  Webhook:
    POST /webhooks/didit (publicRoute)
    Validação: HMAC-SHA256 no header X-Signature-V2 (usando DIDIT_WEBHOOK_SECRET)
    Processamento:
      1. banClassifier → 12 categorias de risco → banimento ou aprovação
      2. Atualiza user_kyc_profiles (status = verified / rejected)
      3. Popula user_identity_profiles (dados biométricos extraídos)
      4. Notifica admins com permissão admin.kyc.review
      5. Provisiona wallet se status = verified (stub: ensureAsaasCustomerStub ⏳)

RESEND — E-mail Transacional
  Endpoint  : api.resend.com/emails
  Auth      : Bearer RESEND_API_KEY
  Consumidor: BullMQ Email Worker (propya.email.delivery)
  Tipos enviados: ver seção 4A

INSTAGRAM GRAPH API — Posts públicos
  Acesso    : server-side via Next.js Route Handler (/api/instagram/posts)
  Não passa pelo Express backend

BLOCKCHAIN SERVICE — [DESABILITADO]
  LEDGER_MODE=db → isOffChainLedger() = true
  Token Settlement Worker nunca inicializa
  finalize-token-settlements chama reconcileOffChainSettlements() (off-chain puro)
  Variáveis BLOCKCHAIN_SERVICE_URL e BLOCKCHAIN_SERVICE_INTERNAL_API_KEY existem
  mas nunca são lidas em produção

7. FLUXOS PRINCIPAIS (fim a fim)
────────────────────────────────────────────────────────────────────────────────

COMPRA DE TOKEN (PIX):
  Browser → POST /token-orders/purchase (JWT)
  → Express cria token_orders (status=pending) + payment_transactions
  → Asaas POST /payments → retorna payment_id + qrCode
  → Resposta ao frontend com qrCode + valor + expiresAt
  → Tenant paga no app bancário
  → Asaas webhook POST /webhooks/asaas/payments (PAYMENT_CONFIRMED)
  → Push na propya.payments.reconcile
  → Payment Reconciler: atualiza payment_transactions (status=confirmed)
  → settle_token_redistribution (RPC off-chain) → wallet_token_balances atualizado
  → token_orders (status=completed)
  → Push na propya.email.delivery → Email Worker → Resend → e-mail ao tenant

KYC (DIDIT):
  Browser → POST /kyc/didit/start (JWT)
  → Express: POST /v3/session/ no Didit → retorna sessionUrl
  → Frontend abre sessionUrl em iframe/redirect
  → Tenant completa biometria
  → Didit webhook POST /webhooks/didit
  → HMAC validado via req.rawBody + DIDIT_WEBHOOK_SECRET
  → banClassifier(result) → decisão: approved / rejected / banned
  → user_kyc_profiles atualizado
  → user_identity_profiles populado
  → Notificação in-app para admins com permissão admin.kyc.review
  → (stub) ensureAsaasCustomer → cria cliente no Asaas para cobranças futuras

EXTRATO PDF:
  Browser → GET /me/wallet + GET /me/profile (paralelo, JWT)
  → FmzWalletStatementPage.tsx monta documento A4 em memória (React)
  → Botão "Imprimir / Salvar PDF" → window.print()
  → @media print oculta toolbar → browser gera PDF sem servidor

DISTRIBUIÇÃO DE ALUGUEL (cron mensal):
  GH Actions → generate-rent-charges.js
  → rent_charges criados para todos os contratos ativos
  → Asaas cria cobranças (boleto ou PIX)
  → Tenant paga → webhook confirma → Payment Reconciler
  → pay-owner-payouts.js (cron periódico)
  → owner_payout_accruals calculados (TWAO — time-weighted average ownership)
  → Asaas POST /transfers → PIX para cada co-owner
